# Assay jobs start through `assay run`, a launcher that runs `harbor run` as a subprocess

`uv run assay run -c jobs/<file>.yaml ...` is the only supported way to start an Assay job. It takes one option of its own, `--overwrite`, and passes every other argument to `harbor run` unchanged and in the same order. Before Harbor starts, it finds the job's results folder, `<jobs_dir>/<job_name>/`. As in Harbor, `--job-name` and `-o`/`--jobs-dir` on the command line win over the job file. Without `--overwrite`, if that folder holds results with a different config, `assay run` stops and says to re-run with `--overwrite`. Harbor itself fails with a `FileExistsError` that does not say how to fix it. With `--overwrite`, it deletes the folder without asking, then runs. We chose a launcher because Harbor (pinned, third party) has no option to overwrite a job's results, and the only fix was to delete the folder by hand.

Harbor runs as a subprocess, not in process, because the layout of Harbor's CLI module is not a public API. The launcher imports only Harbor's `JobConfig` model and its skill resolver, so that it builds the config the same way Harbor does and compares it the same way Harbor does (`existing_config != self.config`). `-c` is required, so that every result traces back to a committed job file. `--overwrite` deletes without a prompt: the flag is already the opt-in, and a prompt that you always answer yes to adds nothing.

## Considered Options

- **Patch or subclass Harbor's `Job`** to overwrite in place: couples Assay to more Harbor internals than ADR 0001 does, and a patch to a pinned third-party package is lost on every upgrade.
- **Call Harbor's CLI in process**: no subprocess, but it depends on the layout of Harbor's CLI module and on Typer's internals.
- **Move the old folder aside instead of deleting it**: keeps the old results, but `results/` fills with stale copies that nothing reads. The job file in git already records what the old run was.
- **No option** (delete by hand, or pass a new `--job-name`): no code, but the error message gives no hint, and a new job name breaks the `results/<job_name>/` path that the README and analysis use.

## Consequences

The config comparison copies a part of Harbor's `build_job_config` and `Job.create` (the job-file load, the legacy migration, the `--job-name`/`--jobs-dir` overrides, and the skill resolution). A Harbor upgrade that changes how it builds the config can make the hint fire when Harbor would resume. The slow test re-runs a finished job through `assay run` to catch that. Other `harbor run` options that change the config (for example `-k`) are not applied to the comparison. A run started with one of them can get the hint on a re-run even when Harbor would resume it. Put such settings in the job file instead. Before Harbor starts, `assay run` also refuses a job whose `InstrumentedClaudeCode` agent has a Claude Code version other than `stable`, `latest` or `X.Y.Z`, such as no version or the placeholder (issue #30). It uses the same check as `InstrumentedClaudeCode.setup()`, so the launcher imports `instruments.agent` too. That check reads the job file only, so a version given with `--ak` is not seen: set it in the job file. `assay run` takes one `-c` only, because Harbor merges several job files with rules that the launcher does not copy.

The analysis tools are `assay` subcommands too (`assay trace-check`, `replay`, `agent-runs`, `trajectory`, `compare-labels`, `summary`; issue #32), and `python -m analyze.<module>` no longer runs them, so `assay` is the one tool for running and analysing a job. Unlike `run`, they run in process: each subcommand passes its arguments to its module's `main(argv)` unchanged.
